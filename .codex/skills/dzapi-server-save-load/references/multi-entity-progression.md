# 多实体成长存档与共享防刷

## 适用场景

用于“每英雄/每角色独立积累整数经验，但所有角色共享每局和每日总获取上限”的成长系统。

## 数据拆分

- 每个实体使用一个独立整数 Key；需要后端验证增长时，不要优先压成字符串。
- Key 保持短、稳定、无分隔符，例如逻辑 Key `HFX01..HFX25`。
- `DzAPI_Map_StoreInteger/GetStoredInteger` 自动添加 `I`，所以上例实际后端 Key 为 `IHFX01..IHFX25`。
- 等级、全实体经验、全实体满级数等派生数据从经验缓存计算，不重复存档。
- 业务身份使用选择/创建阶段固化的稳定实体索引；不要从中途可能变化的技能、天赋或临时形态谓词推断归属。当前单位类型映射只作为校验或兜底。

## 推荐后端结构

安全目标是：阻止玩家凭空增加所有实体的经验总量；允许极少数篡改者在已经获得的合法总量内重新分配实体经验。采用：

```text
IHFX01..IHFX25：25 个非只增实体经验 Key
IHFT：1 个只增的累计总获取 Key
```

后台分别配置：

- 每个 `IHFXxx` 都使用单 Key 防刷：每局最大 4、每日最大 44，不加入只增。
- `IHFT` 使用单 Key 防刷：每局最大 4、每日最大 44，并加入只增存档。
- 不再建立 `IHFX01 + ... + IHFX25` 的多个 KEY 组合公式。
- 正常通关奖励用批量保存同时写入“当前实体经验 + reward”和“累计总获取 + reward”。批量中任一项违反后端规则时，实测两项均不落盘。

每实体的单 Key 限制阻止经验瞬间从一个实体搬到另一个实体；只增总获取 Key 则限制全账号每局及每日真正新增的总经验。地图内校验负责把实体经验总和压回累计授权总量。

## KK 后端实测结论

2026-07-12 在 KK 内测大厅先后使用两组新 Key 实测：

- 单 Key 每日上限生效；达到上限时平台提示 `1274`，下一局确认没有落盘。
- 同一局连续两次增加、累计超过每局上限时提示 `1273`，下一局只保留允许范围内的第一次增加。
- 顺序写先降低 A、再把 B 提高到超过每局差值上限时，A 的降低落盘、B 的提高被 `1272` 拒绝；顺序双写不具备原子性。
- 批量写 `A=8,B=0 -> A=0,B=8` 时，组合总和不变，后端接受并在下一局确认落盘；多个 KEY 逻辑按组合净变化允许经验转移。
- 批量写 `A=4,B=8 -> A=-100,B=108` 时，组合总和下降，后端同样接受；非只增 Key 可用负数抵消大额正增长。
- `DzAPI_Map_SaveServerValue` 和批量接口返回 `true` 只表示调用被接收，不能证明后端防刷通过或成功落盘。
- `DzAPI_Map_GetServerValueErrorCode` 是读档错误码，不是保存错误码；保存是否成功仍以下一局开局快照为准。
- `KKApiGetServerValueLimitLeft` 使用实际后端 Key 可以返回可用额度；整数存档逻辑 Key `H2A` 对应查询 `IH2A`。
- 剩余额度是开局快照：本局保存后立即查询不会变化，下一局才反映扣除。
- 把单 Key 从 4 降回 0 后，其每日剩余额度仍为 4；再次增加 4 后下一局额度为 0。降低不会返还每日额度。
- 两项批量保存中，一项超过单 Key 每局限制时，另一项即使合法也没有落盘；测试范围内批量拒绝是原子的。
- 正向路径中，实体 A 与只增总量 T 分别从 0 增加到 4，下一局确认均为 4，`sum=4`、`excess=0`；A 的剩余额度从 36 降至 32，T 从 44 降至 40。

因此当前项目采用：

- 禁止使用“可下降的多个实体 Key + 仅一个加法组合规则”保护成长值。
- 每实体非只增 Key 分别受单 Key 防刷保护，只消耗一个只增名额给累计总获取 Key。
- 接受作弊者可能在合法累计总量内重新分配实体经验；不接受实体经验总和超过累计总获取。

## 阶段上限与异常修正

当前每英雄 5 级阶段上限例如为 `STAGE1_MAX_XP = 300`：

1. 实体 Key 非只增，读取超过 300 时按 300 缓存并向后端写回 300；这是下降，不消耗或返还增长额度。
2. 读取负数时按 0 参与显示和求和并记录异常；不要直接把巨大负数写成 0，因为这会形成大额正增长并可能被防刷拒绝。
3. 只增总获取 Key 只代表历史累计授权，不直接显示为某英雄经验，也不能绕过 `sum(entityXp) <= totalEarnedXp` 校验。
4. 后续开放更高阶段时仍优先新增阶段 Key，避免旧版本与新版本对同一上限产生不同解释。

实体经验即使被篡改回退，也只能依靠每天最多 44 的后端正增长额度重新增加；这正是用一个只增总量 Key 节省 25 个只增名额时接受的权衡。

## 初始化与写回

- 存档准备完成后一次性读取所有实体 Key；每次读取后立即检查 `DzAPI_Map_GetServerValueErrorCode`。
- 任一关键读档失败时禁止用默认 0 覆盖服务器原值，并停止本局成长写入。
- 缓存区分开局确认值与本局待确认增量；局中再次 `GetStoredInteger` 不能确认写入结果。
- 全部读档成功后计算实体经验总和；若超过累计总获取，从当前经验最高的实体开始确定性地平均化扣除，直到总和合法，再批量写回降低后的实体值。
- 满级或剩余阶段容量为 0 时不调用存档写入，也不消耗后端增长额度。
- 接近阶段上限时只增加 `min(reward, stageMax - cachedXp)`；达到阶段上限后停止。
- 正常奖励必须把实体 Key 与总获取 Key 放在同一个批次中；不要用两个顺序保存替代，因为顺序保存发生拒绝时可能部分落盘。
- `LimitLeft` 只作为开局后端额度快照；局中若需展示，由缓存额度减去本局已提交增量，不通过再次查询确认保存结果。
- 服务器存档写入只在对应玩家的本地客户端执行；本地读写结果不得决定单位、伤害、掉落等同步游戏状态。

## 后端测试文件要求

新建服务器存档 `_Test.j` 时至少提供：

- 一个不参与组合规则的对照 Key，以及两个参与组合规则的 A/B Key。
- 开局快照查询、单 Key 查/增/设、批量同时设置 A/B、顺序设置 A/B。
- Logger 日志：开局值、读档错误码、目标值、单项差值、组合前后总和、批量 begin/add/end 返回值。
- 下一局确认步骤；不要把接口布尔返回值当成落盘结果。
- `KKApiGetServerValueLimitLeft` 查询指令，分别查询测试 Key 在写入前后的返回值；在大厅实测前只记录原始返回值，不预设它对单 Key、组合规则、每天或每周限制的解释。
- 至少测试每日上限、同局累计、批量净值转移、负数抵消、顺序部分落盘，以及“降低后再增加是否返还周期额度”。

## 设计审查清单

- 实体索引是否稳定，皮肤、天赋、变身后是否仍归属正确。
- 逻辑 Key 与实际带类型前缀的后端 Key 是否一致。
- 是否没有建立可被净变化绕过的实体加法组合公式。
- 每个实体 Key 与总获取 Key 是否都具有正确的单 Key 每局/每日上限。
- 是否只有总获取 Key 占用只增名额，且业务不会把它直接换算为实体经验。
- 正常奖励是否使用同一批次双写实体经验和总获取。
- 开局是否只在全部读档成功后执行总和校验与超额扣除。
- 异常高值是否向下截断，负值是否避免形成大额修正性正增长。
- 新等级是否使用新阶段 Key，而不是放宽旧阶段可信上限。
