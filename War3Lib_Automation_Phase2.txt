# War3Lib 自动化测试系统 - 第二阶段实施计划

## 0. 背景

当前分支：

```text
codex/war3-auto-phase1
```

第一阶段已经完成并测试通过：

```text
启动 War3
→ 自动进入局域网
→ 自动创建游戏
→ 自动开始游戏
```

下一阶段目标应该是：

```text
启动第 1 个 War3 作为房主
→ 房主进入局域网并创建房间
→ 启动第 2 个 War3 作为客户端
→ 客户端进入局域网并加入房主房间
→ 房主点击开始游戏
```

也就是从“单窗口自动开始”升级到“本地双开自动进房并开始”。

## 1. Phase1 当前实现分析


这个设计是合理的，因为 Lua 保持为任务编排层，Python 是自动化执行层。


```text

pyautogui.press
pyautogui.hotkey
```

但 Phase1 主流程实际用的是按键，不是点击。


```python
PHASE1_STEPS = (
```

```text

```

## 2. 当前实现是否会被窗口遮挡影响？

会。

原因是当前截图函数使用的是：

```python
mss.grab({
    "left": left,
    "top": top,
    "width": width,
    "height": height
})
```

它抓取的是屏幕坐标区域，不是直接抓取某个 HWND 的后台窗口内容。也就是说：

```text
如果 War3 窗口被其他窗口盖住
截图里看到的是盖在上面的窗口
模板匹配就会失败
```

如果 War3 被最小化，也无法通过当前方式稳定识别。

当前流程虽然会调用：

```text
activate_window(hwnd)
```

让 War3 到前台，但它仍然属于前台自动化，不是后台自动化。

结论：

```text
Phase1 当前方案必须保证目标 War3 窗口可见、可激活、没有被遮挡。
```

---

## 3. 如果扩展到 6 个窗口，会不会互相遮挡？

会，而且这是 Phase2 / Phase3 必须提前解决的问题。

当前方案的几个限制：

### 3.1 只有一个前台输入焦点

`pyautogui.press()` / `pyautogui.hotkey()` 是全局输入，按键会发给当前前台窗口。  
所以同一时刻只能可靠操作一个 War3 窗口。

这不代表不能多开，而是意味着多窗口操作必须按顺序：

```text
激活窗口 A
→ 等待图像
→ 发送按键
→ 激活窗口 B
→ 等待图像
→ 发送按键
```

不能同时并发操作 6 个窗口。

---

### 3.2 窗口重叠会影响截图识别

因为当前 `mss` 是屏幕区域截图，所以如果 6 个窗口互相覆盖，后面的窗口被挡住，识别就会失败。

---

### 3.3 多窗口标题可能无法区分

当前 `find_war3_window()` 是按标题关键词查找 War3 窗口，并返回第一个匹配窗口。多开后多个窗口标题可能一样，因此必须引入更稳定的窗口身份管理。

比如：

```text
按启动时间区分
按 PID 区分
按窗口位置区分
按 hwnd 列表差集区分
```

---

### 3.4 6 窗口的屏幕空间问题

如果每个 War3 窗口都是 1280x720，6 个窗口不可能在普通屏幕上完全不遮挡。

可选方案：

```text
方案 A：所有窗口依次置顶操作，不要求同时可见
方案 B：把窗口缩小并平铺
方案 C：使用虚拟桌面/多显示器
方案 D：后期探索后台截图/后台消息
```

对当前阶段来说，推荐方案 A + B：

```text
Phase2 先做 2 个窗口
Phase3 再扩展 6 个窗口
```

---

## 4. 解决方案分析

### 4.1 当前最推荐方案：顺序前台控制

核心思路：

```text
每次只操作一个窗口
操作前先激活目标窗口
目标窗口被激活后自然会到最前面
然后截图识别
然后发送快捷键或点击
```

优点：

```text
实现简单
和 Phase1 兼容
不涉及 Hook
不涉及后台消息
稳定性较高
```

缺点：

```text
不能并发操作
速度较慢
窗口会来回切换
6 窗口时会有闪烁
```

这个方案适合 Phase2。

---

### 4.2 固定窗口布局

Phase2 应该先引入窗口布局管理。

建议：

```text
房主窗口：左上角
客户端窗口：右上角
```

例如：

```text
host:   x=0,   y=0, width=960, height=540
client: x=960, y=0, width=960, height=540
```

如果屏幕不够大，可以使用：

```text
host:   x=0, y=0,   width=800, height=600
client: x=0, y=620, width=800, height=600
```

注意：War3 老版本对窗口缩放/分辨率可能不完全友好，所以 Phase2 不要强制依赖超小窗口。应允许用户在配置中调整。

---

### 4.3 使用 PID / HWND 绑定窗口

Phase2 必须解决：

```text
多个 War3 窗口标题相同，怎么知道哪个是 host，哪个是 client？
```

推荐实现：

1. 启动 host 前，记录已有 War3 窗口列表。
2. 启动 host 后，等待新窗口出现。
3. 用新窗口集合减去旧窗口集合，得到 host hwnd。
4. 启动 client 前，再记录窗口列表。
5. 启动 client 后，再做一次差集，得到 client hwnd。

伪代码：

```python
before = list_war3_windows()
launch_war3()
after = wait_new_war3_window(before)
host = after.new_window

before = list_war3_windows()
launch_war3()
after = wait_new_war3_window(before)
client = after.new_window
```

不要只靠：

```text
find_war3_window()[0]
```

否则多开后会随机拿到错误窗口。

---

### 4.4 后台截图 / 后台点击是否要做？

不建议 Phase2 做。

后台截图可以研究：

```text
PrintWindow
Windows.Graphics.Capture
DwmGetWindowAttribute
```

后台点击可以研究：

```text
PostMessage
SendMessage
WM_LBUTTONDOWN
WM_LBUTTONUP
WM_KEYDOWN
WM_KEYUP
```

但这些对游戏窗口不一定稳定，尤其 DirectX / 全屏 / 独占输入环境下经常失效。  
而且一旦接近注入、Hook、平台环境，就会复杂很多。

Phase2 目标是先把双开链路跑通，不要在这里引入后台自动化。

推荐实现逻辑：

```python
def wait_new_war3_window(before_hwnds, title_keywords, timeout_seconds):
    deadline = time.monotonic() + timeout_seconds
    while time.monotonic() < deadline:
        windows = list_windows(title_keywords)
        for window in windows:
            if window.hwnd not in before_hwnds:
                return window
        time.sleep(0.5)
    raise TimeoutError("New Warcraft III window not found")
```

## 10. Phase2 详细流程设计

### 10.1 Host 创建房间

复用 Phase1 的前半段：

```text
host:
等待 lan_button.png
按 L

等待 create_game.png
按 C

等待 create_game2.png
按 C
```

不要立即执行：

```text
start_game
```

也就是说 Phase2 需要把 Phase1 拆成多个可复用 step：

```python
goto_lan(session)
create_game(session)
start_game(session)
```

而不是一个固定 `PHASE1_STEPS` 一路跑到底。

---

### 10.2 Client 加入房间

推荐第一版先用简单流程：

```text
client:
等待 lan_button.png
按 L

等待 join_game.png 或 room_list_ready.png
按 Enter / J / 双击第一个房间
```

这里需要根据你的 War3 UI 实际按键确认。

可选方案：

#### 方案 A：快捷键加入

如果局域网房间列表默认选中第一个房间：

```python
press_key("enter")
```

或者：

```python
press_key("j")
```

优点：

```text
简单
不依赖点击坐标
```

缺点：

```text
需要确认 War3 UI 默认焦点
```

#### 方案 B：点击第一个房间 + 加入按钮

新增配置：

```python
first_room_click_offset = (x_ratio, y_ratio)
join_button_template = "join_game.png"
```

流程：

```text
等待房间列表出现
点击第一行房间
等待加入按钮
点击或按快捷键加入
```

优点：

```text
更直观
```

缺点：

```text
需要坐标/模板
```

Phase2 建议先用方案 B，因为更可控。

---

### 10.3 Host 开始游戏

client 加入后，切回 host：

```text
activate host
等待 start_game.png
按 Alt+S
```

这里建议不要一开始就 OCR 判断人数。

Phase2 简化判断：

```text
client 执行加入流程后
等待 2~3 秒
host 等待 start_game.png
按 Alt+S
```

后面 Phase3 再加：

```text
识别玩家人数

识别开始按钮是否可用
```

## 11. 窗口遮挡问题的 Phase2 处理策略

Phase2 采用：

```text
顺序前台控制
```

即：

```text
每次操作目标窗口前：
1. activate_window(hwnd)
2. 等 0.2~0.5 秒
3. get_window_rect(hwnd)
4. mss 截图
5. 模板匹配
6. 按键/点击
```

因为激活窗口会把目标窗口置前，所以即使 host/client 互相遮挡，也能顺序操作。

但是要注意：

```text
截图匹配必须发生在 activate_window 之后
```

否则可能截到被遮挡状态。

## 12. 6 窗口扩展方案预研

Phase2 暂不实现 6 窗口，但要避免把代码写死成 2 窗口。

建议从 Phase2 就设计为：

```python
clients = [
    "client1",
]
```

而不是：

```python
client = ...
```

未来 Phase3 可以改成：

```python
clients = [
    "client1",
    "client2",
    "client3",
    "client4",
    "client5",
]
```

长期 6 窗口流程：

```text
host 创建房间
for client in clients:
    启动 client
    client 加入房间

host 等待所有 client 加入
host 开始游戏
```

未来 6 窗口时，推荐仍然是顺序操作：

```text
操作 client1
操作 client2
操作 client3
操作 client4
操作 client5
操作 host
```

不建议一开始做并发。

## 19. 关键注意事项

### 19.1 不要并发操作窗口

Phase2 不要开线程同时控制两个 War3。

必须顺序执行：

```text
host
client
host
```

---

### 19.2 不要一开始做 6 窗口

6 窗口是 Phase3 或 Phase4。

Phase2 只做：

```text
1 host + 1 client
```

---

### 19.3 不要依赖 Popen.pid 识别 War3

因为当前是通过：

```text
YDWEConfig.exe
```

启动 War3。

`subprocess.Popen` 返回的可能是 YDWEConfig 进程，不一定是最终 War3 窗口对应的 PID。

应该用：

```text
启动前后的窗口差集
```

绑定 hwnd。

---

### 19.4 不要做后台点击

Phase2 继续使用：

```text
activate_window
mss 截图
opencv 匹配
pyautogui 输入
```

后台点击留到后续研究。

# 总结

Phase1 当前是：

```text
截图识别状态
→ 发送快捷键
→ 单窗口自动开始
```

它会受窗口遮挡影响，因为截图来自屏幕区域，不是后台窗口内容。

Phase2 应该做：

```text
双开
窗口绑定
窗口布局
host 创建房间
client 加入房间
host 开始游戏
```

最推荐的实现策略是：

```text
继续使用前台顺序控制
不要做后台点击
不要做网络层
不要直接上 6 窗口
```

Phase2 的核心不是“图像识别更复杂”，而是：

```text
可靠地区分多个 War3 窗口
并把 host/client 流程拆开编排
```
