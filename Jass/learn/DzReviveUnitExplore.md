# DzReviveUnit 交互探索

当前只有测试工具，没有游戏内结论，不接入 Xlimon。主库保持为空。
入口为同目录 `DzReviveUnitExplore_Test.j`，`Jass/config/UnitTest.h` 已切到此测试。
构建模式为 VERSION_UNITTEST，空白地图；编辑器任务使用 `🥭启动:单元测试-vjassc`。

## 第一轮建议

请重新启动测试地图，确认屏幕显示 **v2 已加载**。旧局不会自动更新。

最简单的操作：输入一次 `-all`，自动顺序运行 s1 → s5 → s6 → s2 → s3（默认约5分钟）。
每项之间间隔2秒；失败时停止后续项目，保留现场并提示发送日志。整套不包含性能和删除边界。
若只想先看懂过程，输入一次 `s1`，不用继续操作：

1. 0秒：创建活步兵，显示完整流程。
2. 2秒：杀死步兵，提示即将复活。
3. 5秒：调用API，记录原始状态；若仍死亡则提示失败并结束，否则恢复显示等状态、向右移动。
4. 10秒：检查移动，通过伤害再次杀死，检查两次死亡事件和受伤监听。
5. 13秒：再次复活并保留单位，显示 END。

也可以依次输入 `s1`、`s5`、`s6`、`s2`、`s3`，每个命令等屏幕出现对应的 END 后再输入下一个。
新 s 命令会清理旧实验并开始新的一组，只有 s4 是操作当前尸体组。
自动测试期间不要攻击或操纵实验单位。最好先单客户端运行。

| 指令 | 游戏时间 | 内容 |
| --- | --- | --- |
| s1 | 13 秒 | 有中文阶段提示的完整演示；验证同句柄、移动、再次死亡与再次复活；失败时提前结束 |
| s5 | 3 秒 | 两个牧师分别传入 HP/MP=123/37、0.5/0.25；第一只改为操作者所属；复活位置向右移动600；立即记录实测值 |
| s6 | 3 秒 | 步兵添加狂战士并施放，确认 Bbsk Buff，设置20秒冷却、150移速、userData=24680、暂停及0.5倍动画速度；分别记录死亡前、刚死亡、复活前、复活后状态 |
| s2 | 100 秒 | 同一个步兵受伤致死与复活100轮；同一组单位死亡、玩家死亡、单位受伤触发器只注册一次 |
| s3 | 默认180秒 | 六组尸体保留对照，每30秒记录状态并显示等待进度，到时尝试复活仍有效的对象 |
| s4 | 立即 | 提前复活当前 s3 尸体组；会失去原本长时间等待的验证，正常第一轮不用输入 |
| s7 | 手动 | 创建己方无敌圣骑士与敌方步兵，验证真实攻击、击杀者、经验、赏金以及复活后的战斗 |
| s8 | 60 秒 | 100个步兵、300轮：KillUnit后RemoveUnit，再CreateUnit |
| s9 | 60 秒 | 100个步兵、300轮：KillUnit后DzReviveUnit，不使用显示/动画等修复 |
| s10 | 1 秒 | 独立边界：死亡、RemoveUnit，保留变量1秒后调用DzReviveUnit。最后另开一局测试 |

辅助命令：

- `-help`：显示命令说明。
- `-all`：自动顺序运行基础整套，失败即停；手动输入其他s指令会退出自动队列。
- `-status`：记录当前每只单位的完整状态，以及圣骑士经验、玩家金币和相对本组开始的增量。
- `-stop`：停止计时器，销毁本组单位及专属事件触发器，恢复改过的联盟与赏金开关。
- `-hold 300`：将下一组 s3 的等待时间设为300秒；范围10～900秒，不修改正在运行的一组。

## 尸体六组

| 槽位 | 操作 |
| --- | --- |
| 1 | 不隐藏、不暂停腐烂 |
| 2 | 死亡回调里仅隐藏 |
| 3 | 死亡回调里仅 UnitSuspendDecay(true) |
| 4 | 死亡回调里隐藏并暂停腐烂 |
| 5 | 死亡回调里隐藏，0.1秒后暂停腐烂 |
| 6 | 死亡回调里隐藏，5秒后暂停腐烂 |

5秒是固定时间采样，并非已经验证的腐烂阶段检测。只测试原生步兵默认死亡设定。
若180秒时未经处理的对照也没消失，输入 `-hold 300` 后重跑 s3；不足以据此证明长期保留成功。
普通实验遇到 GetUnitTypeId=0 会记录 SKIP/expired 并跳过复活。只有 s10 故意向已移除对象调用API。
自动组会临时设置双方被动联盟，避免中立AI干扰；s7恢复敌对测试，结束清理时还原原联盟。

## 手动战斗 s7

1. 输入 s7，再输入 -status 记录起点。
2. 用圣骑士普通攻击杀死步兵，输入 -status。
3. 输入 -revive，再用圣骑士普通攻击杀死它，再输入 -status；重复数轮。
4. 再复活，分别用 -damage（圣骑士伤害致死）和 -kill（KillUnit）对照，每次死后记录 -status。
5. 如果原始复活后隐藏、暂停或动画不正常，先 -status 保存证据，再用 -restore 尝试恢复。

`-kill`、`-damage`、`-revive`、`-restore` 只在 s7 有效。
不要把 KillUnit 的击杀者与赏金行为预设成和普通攻击一致。
测试单位具有模型与碰撞，但碰撞、选中和动画仍需手动观察，日志不替代视觉验证。

## 日志如何判读

v1日志作废：省略花括号的控制语句在当前编译器下生成了错误流程，导致聊天注册16次、复活调用丢失以及结束分支不可达。
v2已将控制语句全部加花括号，并检查生成JASS中的事件注册、复活调用和独立计时分支。编译通过仍不代表游戏内通过。

搜索统一前缀 `[DzReviveExplore]`；run编号区分每次重跑，mode对应s编号。
日志通过项目 Trace 写入 jass.log，并显示在调试控制台。
项目 `script/init.lua` 将日志目录设为游戏工作目录下的 `War3Lib\日志\`，使用当前会话日志文件。
将整段 BEGIN～END 连同报错发回，优先提供完整日志文件；另注明游戏/KK环境，以及看见的动画或控制异常。

- RAW_AFTER_API / CORPSE_RAW_AFTER_API / MANUAL_RAW_AFTER_API：没有做额外状态恢复的原始结果。
- 自动功能实验记录原始结果后，会显式取消暂停腐烂、显示、取消暂停、恢复动画速度和stand动画。之后的移动成功不能证明API自动处理了这些状态。
- s7 的 -revive 和 s9 刻意不执行这些恢复操作。
- DEATH_UNIT、DEATH_PLAYER：独立计数，监听器不会在复活时重新注册。
- DAMAGE：原始受伤事件、来源与伤害量。s2每轮至少一次伤害事件，两类死亡事件各一次。
- s6 中 fixture Buff没建立或冷却设置失败时，该项不能用于推导复活的清理行为；先修正实验条件。
- s5的小数值生存结果只作观察，不预设参数是点数、比例还是百分数。
- 句柄ID只是辅助证据，必须结合类型、存活、移动、再次伤害及死亡判断。
- END failures=0不代表所有API语义已确认，也不代表Xlimon所有自定义死亡回调都兼容。

## 性能与删除边界

s8/s9记录创建次数、死亡总数及本机平均FPS；不为每只单位注册专属触发器，避免两种路径的监听成本不一致。
FPS只用于日志，不参与同步分支。它不是精确CPU耗时或内存测量；固定帧率时两者都高不代表无差异。
建议分别新开游戏测 s8、s9，保持镜头、设置相同，再反序复测；若关心内存，同时记录进程开始/结束的内存。

s10可能导致无效调用、脚本中断或游戏崩溃，因此与正常实验分离。
日志有 REMOVE_BEGIN、REMOVE_DONE、REMOVED_API_CALL_BEGIN、REMOVED_API_CALL_RETURNED 四个阶段标记。
发生异常时保留最后日志。即便它某次返回，也不能据此将“删除后复活”作为生产池契约。

运行日志确认基础行为后，再决定是否增加物编死亡类型矩阵、长时间复用、双客户端与Xlimon死亡清理集成测试。
