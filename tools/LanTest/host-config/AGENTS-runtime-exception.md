## Warcraft 自动测试例外

- 允许通过 War3Lib 启动器及 D:/War3/tools/LanTest 的 CLI 运行测试，允许 YDWE 的 `-auto` 组件内部自动入房。此例外不允许通用桌面控制、截图点击、SendKeys 或旧 Python/war3auto 回退。
- 自动测试完成、失败或超时后，保存日志并使用 Codex-War3-StopTest 计划任务关闭本次记录的游戏 PID/创建时间；只清理本次房主。人工启动保留游戏，不自动结束。
- 同一游戏环境只运行一场自动测试；以日志完成标记和断言/OOS 证据验收，不以进程启动或没有掉线判通过。

- 默认自动 Warcraft 测试使用 `Start-LanTest.ps1 -Automated -OwnerId <任务标识>`，自动选择空闲 A/B 环境；都忙时排队，释放后自动接续。`-PoolEnvironment A|B` 可指定环境，直接 `pool/Start-PoolTest.ps1` 也使用同一分配队列。不同环境允许并行，同一环境禁止绕过队列。等待时继续不依赖游戏的工作，不重复启动同一测试。
- 其他 agent 占用一个环境时可自动使用另一个；候选环境均忙或存在人工/未知归属/旧入口游戏时只等待，不要求用户关闭魔兽，也不代替其他任务清理。队列超时记为 DEFERRED，明确运行验证尚未完成。
- 清理由本次自动测试的拥有者在 finally 中执行，传入匹配 OwnerId 并核对 PID/创建时间；死队列记录可跳过，但不能据此清理孤儿游戏。FINISHED 队列状态不代表测试或清理成功，须检查 result.json / cleanup.json。
- A/B 池使用固定目录、配置与端口；占用期间不重建或覆盖运行文件。项目测试传入 ProjectPath，CloudScripts 和本地 INI 起始数据复制到私有环境，日志映射到分配的游戏目录；测试写入不回写人工环境。跨局存档测试需明确准备测试数据，不能依赖自动分配到某个环境。
- 双场自动入房与归属清理已验收，人工游戏同时运行尚未验收，不得声称已证明互不影响；不得结束人工或未知归属进程。
- War3Lib 人工启动仅排除确认属于 A/B 私有环境的占用；同一人工环境和未知归属游戏仍保护。启动确认必须匹配本次父启动器及创建时间，不能把已有池客户端视为新启动成功。
- War3Lib 启动成品固定覆盖 `Output/UnitTestMap_slk.w3x`，通过当前入口/引擎清单校验复用。自动任务先冻结地图再排队，归属清理成功后删除本次地图副本；不为每次测试永久保留 w3x。清理 Output 必须检查活跃任务、文件占用和路径归属，保留源码、结论及当前产物。
